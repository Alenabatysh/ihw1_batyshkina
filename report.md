## 1. Условие задачи

Разработать многопоточную имитационную программу на языке C, моделирующую процесс обслуживания покупателей в супермаркете. Программа должна использовать библиотеку `pthread` и синхропримитивы (мьютексы и семафоры) для согласованного асинхронного взаимодействия потоков, обеспечивать наглядное представление результатов в реальном времени и корректно завершаться при любых входных данных, включая прерывание по сигналу.

Ключевые сущности предметной области:
- Покупатели, прибывающие в супермаркет в случайные моменты времени;
- Кассы с очередями ограниченной вместимости;
- Кассиры, обслуживающие покупателей.

Параметры модели задаются через конфигурационный файл и включают количество покупателей, вместимость очередей, временные интервалы, стратегию выбора очереди, продолжительность рабочего дня и множитель времени (`time_scale`) для регулировки скорости симуляции.

## 2. Сценарий моделирования

### 2.1. Отображение сущностей в потоки

В программе принята многопоточная архитектура. Каждая сущность предметной области, обладающая поведением, реализована как отдельный независимый поток POSIX (`pthread_t`).

| Сущность предметной области | Представление в программе | Поведение (поток) |
|-----------------------------|---------------------------|-------------------|
| Покупатель | структура `Customer` + `pthread_t` | Отдельный поток: имитация выбора товаров (`usleep`), захват мьютексов очередей для выбора стратегии, ожидание обслуживания (`sem_wait` / `pthread_cond_wait`), завершение. |
| Кассир | структура `Cashier` + `pthread_t` | Отдельный поток: бесконечный цикл ожидания клиента, обслуживание (`usleep`), сигнализация клиенту об окончании (`sem_post` / `pthread_cond_signal`). |
| Генератор | функция `generator_thread_func` | Отдельный поток: создает потоки покупателей с заданным случайным интервалом, устанавливает флаг `entrance_closed` по исчерпанию лимита. |
| Дисплей | функция `display_thread_func` | Отдельный фоновый поток: периодически (каждые 50 мс) считывает состояние симуляции под защитой мьютексов и обновляет консоль через ANSI escape-последовательности. |

### 2.2. Жизненный цикл покупателя (потока)

1. **Прибытие:** Поток-генератор инициализирует параметры покупателя (ID, количество товаров) и запускает его поток.
2. **Выбор товаров:** Поток покупателя вызывает `usleep` на случайное время из диапазона `[shopping_time_min, shopping_time_max]`.
3. **Выбор очереди:** Поток последовательно блокирует мьютексы обеих очередей (во избежание deadlock), сравнивает их размеры согласно стратегии (SHORTEST/FIRST/RANDOM) и выбирает целевую очередь.
4. **Вставание в очередь:** Поток блокирует мьютекс выбранной очереди. Если очередь переполнена (`size >= capacity`), поток увеличивает счетчик `total_left_no_service` и завершается. Иначе добавляет свой ID в массив очереди.
5. **Пробуждение кассира:** Поток вызывает `sem_post` (или `pthread_cond_signal`) для семафора/условной переменной кассира, сигнализируя о появлении клиента.
6. **Ожидание обслуживания:** Поток блокируется на `sem_wait` (или `pthread_cond_wait`), ожидая сигнала от кассира.
7. **Завершение:** Кассир обслуживает покупателя и вызывает сигнал. Поток покупателя разблокируется, обновляет свое время ожидания и корректно завершается.

### 2.3. Взаимодействие потоков

В отличие от последовательной версии (ИДЗ-1), где события хранились в min-куче и обрабатывались в одном потоке, в многопоточной версии (ИДЗ-2) все сущности работают параллельно. Синхронизация осуществляется через мьютексы (для защиты общих данных от гонок) и семафоры/условные переменные (для сигнализации о событиях между потоками).

### 2.4. Механизмы синхронизации

Для обеспечения корректного асинхронного взаимодействия потоков использованы следующие примитивы:
1. **Мьютексы (`pthread_mutex_t`)**:
   - `sim->stats.mutex`: защищает глобальную статистику от гонок данных (data race) при одновременном обновлении разными потоками.
   - `sim->queues[i].mutex`: защищает массив `customer_ids` и счетчик `size` очереди при добавлении/удалении покупателей.
   - `rng_mutex` (в `rng.c`): защищает вызов `rand()` от одновременного доступа нескольких потоков покупателей, обеспечивая потокобезопасность генератора случайных чисел.
2. **Семафоры (`sem_t`) / Условные переменные (`pthread_cond_t`)**:
   - `cashier->customer_ready` / `customer_cond`: используется кассиром для ожидания появления покупателя. Поток покупателя вызывает сигнал при вставании в очередь.
   - `customer->service_done` / `service_cond`: используется потоком покупателя для ожидания завершения обслуживания. Поток кассира вызывает сигнал после окончания `usleep`.

## 4. Описание пользовательского интерфейса

### 4.1. Конфигурационный файл

Параметры задаются в текстовом файле в формате `ключ = значение`. Строки, начинающиеся с `#`, считаются комментариями. Пример:

```
total_customers = 50
queue_capacity = 5
shopping_time_min = 10
shopping_time_max = 30
arrival_interval_min = 2
arrival_interval_max = 5
items_min = 1
items_max = 8
item_service_time = 15
queue_strategy = 0
work_day_duration = 1800
random_seed = 42
display_delay_ms = 100
time_scale = 1
```

Параметр queue_strategy принимает значения: 0 — SHORTEST (кратчайшая очередь), 1 — FIRST (первая очередь), 2 — RANDOM (случайный выбор).
Параметр time_scale — множитель времени для замедления симуляции в целях визуального наблюдения (1 = реальное время).
Параметр display_delay_ms — задержка обновления дисплея в миллисекундах (используется в последовательной версии; в многопоточной версии задержка жёстко задана 50 мс в потоке дисплея).

### 4.2. Табличный интерфейс в реальном времени

Во время выполнения симуляции в терминале отображается таблица, обновляющаяся на месте без прокрутки. Отрисовка осуществляется в отдельном фоновом потоке (display_thread_func), который каждые 50 мс считывает состояние симуляции, захватывая мьютексы очередей и статистики, и выводит обновлённую таблицу с помощью ANSI escape-последовательностей. Это позволяет наблюдателю понимать происходящее в каждый момент времени без блокировки рабочих потоков.

```
|==========================================================|
| SUPERMARKET SIMULATION                                   |
| Time: 0245 / 1800                                        |
|==========================================================|
| Arrived: 28   Served: 12   Left: 16                      |
|==========================================================|
| Cashier 0: [C2][C5][C8]              serving C2          |
| Cashier 1: [C3][C7]                sleeping              |
|==========================================================|
| Recent events:                                           |
| [0244] FINISH_CHECKOUT        entity=0                   |
| [0244] START_CHECKOUT         entity=0                   |
| [0240] CUSTOMER_ARRIVE        entity=27                  |
|==========================================================|

```
Таблица содержит:
- Заголовок с текущим модельным временем и прогрессом рабочего дня;
- Сводную статистику (прибыло, обслужено, ушло);
- Состояние каждой кассы (список покупателей в очереди и статус кассира);
- Пять последних событий.

### 4.3. Лог-файл

Параллельно с табличным интерфейсом ведётся подробный лог в файле simulation.log. Запись в лог осуществляется конкурентно из потоков покупателей, кассиров и генератора. Для предотвращения перемешивания строк (data race) используется системный вызов write() с атомарными буферами фиксированного размера (1024 байта), что гарантирует целостность каждой записи. В лог записываются все события с временными метками, детальным описанием действий потоков и итоговая статистика.

## 6. Результаты работы программы

### 6.1. Пример запуска

При конфигурации: 50 покупателей, вместимость очереди 5, стратегия FIRST, seed = 42.

**Итоговая статистика:**

```
******************************
    SIMULATION STATISTICS    
Simulation duration:   1800 sec
Total arrived:         50
Total served:          6
Total left (no serv.): 44
Average wait time:     174.83 sec
Max queue 0 size:      5
Max queue 1 size:      0
Cashier 0 served:      6
Cashier 1 served:      0
******************************
Conservation law verified: 50 = 6 + 44

```

### 6.2. Сравнение стратегий выбора очереди

| Стратегия | Обслужено | Ушло без обслуживания | Эффективность |
|-----------|-----------|----------------------|---------------|
| FIRST (все в первую очередь) | 6 | 44 | 12% |
| SHORTEST (кратчайшая очередь) | ~45 | ~5 | ~90% |
| RANDOM (случайный выбор) | ~25 | ~25 | ~50% |

Стратегия SHORTEST демонстрирует наилучшие показатели, так как равномерно распределяет нагрузку между кассами. Стратегия FIRST приводит к перегрузке первой очереди и массовому уходу покупателей.

### 6.3. Результаты тестирования

Автоматизированный тестовый набор включает 18 тестов:

- 13 позитивных тестов (различные конфигурации, граничные случаи, стресс-тесты);
- 5 негативных тестов (невалидные параметры, отсутствующий файл).

Все 18 тестов завершаются успешно. Закон сохранения покупателей соблюдается во всех сценариях.

## 7. Реализация альтернативных синхропримитивов

Для выполнения требования о реализации программы с использованием других синхропримитивов вместо семафоров, была применена условная компиляция.

В Makefile настроены две цели сборки:
- supermarket (использует семафоры POSIX sem_t).
- supermarket_condvar (использует условные переменные pthread_cond_t).

В исходном коде (types.h, simulation.c, threads.c, main.c) с помощью директив #ifdef USE_CONDVAR реализовано ветвление логики синхронизации. Это позволило создать два различных исполняемых файла на основе единой кодовой базы, что демонстрирует владение различными механизмами синхронизации потоков и соблюдение принципа DRY (Don't Repeat Yourself). Обе версии программы проходят все 18 автоматизированных тестов.

## 8. Выводы

В ходе выполнения задания разработана многопоточная программа моделирования работы супермаркета на языке C. Реализованы следующие ключевые механизмы:
1. Многопоточная архитектура: каждая сущность (покупатель, кассир, генератор, дисплей) реализована как отдельный поток POSIX.
2. Синхронизация: корректное взаимодействие потоков без гонок данных с использованием мьютексов и семафоров/условных переменных.
3. Потокобезопасный генератор случайных чисел: защита rand() через мьютекс.
4. Многопоточный табличный интерфейс: обновление в реальном времени через отдельный поток дисплея.
5. Ввод-вывод через системные вызовы: open, read, write, close.
6. Корректная обработка прерываний: через сигнал SIGINT с использованием async-signal-safe функций.
7. Автоматизированное тестирование: 18 тестов, все проходят, инварианты соблюдаются.

Программа корректно завершается при любых входных данных, включая невалидные конфигурации и прерывание пользователем. Результаты моделирования подтверждают, что стратегия SHORTEST обеспечивает наибольшую пропускную способность супермаркета по сравнению со стратегиями FIRST и RANDOM.
