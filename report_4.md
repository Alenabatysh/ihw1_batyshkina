## 1. Условие задачи и цель работы

В качестве предметной области сохранён вариант 8 из ИДЗ-3: имитация работы супермаркета с покупателями, двумя кассирами и очередями ограниченной вместимости. Покупатели приходят в магазин, выбирают товары, занимают одну из очередей и ожидают обслуживания. Кассиры последовательно обслуживают покупателей. При переполнении обеих очередей покупатель покидает магазин без обслуживания.

В ИДЗ-4 к существующей модели добавлено взаимодействие по протоколу TCP. Система разделена на сетевой сервер и независимые клиентские приложения. Клиенты-наблюдатели получают комплексное состояние моделируемой системы. Требуется поддерживать несколько одновременных клиентов и их динамическое отключение и повторное подключение без остановки симуляции.

Реализация выполнена на языке C для Linux с использованием libc, POSIX API и TCP-сокетов.

## 2. Архитектура решения

Существующая модель ИДЗ-3 не переписывалась: она по-прежнему использует POSIX-разделяемую память и именованные POSIX-семафоры. Добавлен отдельный сетевой контур.

| Компонент | Исполняемый файл / роль | Назначение |
|---|---|---|
| Генератор | `supermarket_named generator` | Создаёт процессы покупателей и закрывает вход в магазин после завершения генерации |
| Кассиры | `supermarket_named cashier 0` и `cashier 1` | Извлекают покупателей из очередей и выполняют обслуживание |
| Publisher | `supermarket_named publisher <server_ip> <port>` | Читает состояние общей модели и передаёт снимки по TCP-соединению |
| Сервер | `supermarket_server [bind_ip] [port]` | Принимает publisher и множество клиентов-наблюдателей, хранит последний снимок и рассылает обновления |
| Клиенты | `supermarket_client <server_ip> <port>` | Независимо отображают комплексное состояние супермаркета |

Publisher выполняет роль источника состояния. Сервер не управляет покупателями и кассирами и не вмешивается в алгоритм симуляции. Клиенты являются наблюдателями и не изменяют состояние модели. Благодаря этому отключение наблюдателя не влияет на генератор, очереди или обслуживание покупателей.

### 2.1. Схема взаимодействия

```text
                   POSIX shared memory + named semaphores
        +-----------------------------------------------------------+
        |                                                           |
        |  generator       cashier 0       cashier 1                |
        |      |               |               |                    |
        |      +---------------+---------------+                    |
        |                      |                                    |
        |                supermarket state                          |
        |                      |                                    |
        |                  publisher                                |
        +----------------------|------------------------------------+
                               | TCP: snapshots
                               v
                      +------------------+
                      |  TCP server      |
                      |  poll(), cache   |
                      +------------------+
                        /       |       \
                       /        |        \
                  TCP /     TCP |     TCP \
                     v          v          v
                 client 1   client 2   client N
                 observer   observer   observer
```

Все процессы, использующие один объект POSIX shared memory, располагаются на одном компьютере. Сервер и клиенты могут находиться на отдельных компьютерах в той же сети.

## 3. Реализация TCP-взаимодействия

### 3.1. Формат протокола

Используется TCP как потоковый протокол. Поскольку TCP не сохраняет границы отдельных сообщений, в приложении введено простое кадрирование: каждое сообщение завершается символом новой строки `\n`.

При подключении отправитель сообщает свою роль:

- publisher: `PUBLISHER supermarket-simulation`;
- наблюдатель: `OBSERVER observer`.

Publisher затем регулярно отправляет снимок состояния в формате:

```text
S|sequence|time|duration|arrived|served|left|q0size|q0ids|q1size|q1ids|c0sleep|c0customer|c1sleep|c1customer|finished
```

Поля содержат номер снимка, модельное время, длительность рабочего дня, количество прибывших/обслуженных/ушедших покупателей, размеры и состав двух очередей, состояние обоих кассиров и признак завершения симуляции. Состав очереди передаётся списком ID через запятую; пустая очередь обозначается `-`.

### 3.2. Сервер

Сервер реализован в `src/network_server.c`. Он:

1. Создаёт TCP listening socket, выполняет `bind()` и `listen()`.
2. Принимает новые подключения через `accept()`.
3. Переводит клиентские сокеты в неблокирующий режим.
4. Использует `poll()` для мультиплексирования входящих и исходящих данных всех подключений.
5. Распознаёт роли publisher и observer.
6. Получает снимки от publisher, сохраняет последний снимок и ставит его в очередь отправки каждому подключённому observer.
7. При новом подключении observer отправляет ему последний сохранённый снимок, даже если он подключился не в начале моделирования.
8. При закрытии сокета освобождает только ресурсы соответствующего клиента.

Для одного экземпляра модели допускается один publisher и до 63 наблюдателей одновременно; общий предел сервера - 64 подключения. Выходные очереди клиентов независимы. Если очередь конкретного медленного наблюдателя переполняется, сервер отключает только это соединение. Это сохраняет границы строковых TCP-сообщений и не блокирует publisher или остальных наблюдателей. Отключённый наблюдатель может подключиться повторно и получить последний сохранённый снимок.

### 3.3. Publisher

Publisher реализован в `src/network_publish.c` и вызывается через роль `publisher` в `src/main.c`. Процесс подключается к серверу и с заданным интервалом считывает состояние модели.

Для чтения используются те же именованные семафоры, которыми защищаются исходные поля разделяемой памяти: `MUTEX_TIME`, `MUTEX_STATS` и `MUTEX_QUEUE(i)`. Счётчик прибывших покупателей изменяется и читается под `MUTEX_STATS`; модельное время — под `MUTEX_TIME`. Снимок включает общую статистику, очередь каждого кассира и состояние обслуживания. При потере TCP-соединения publisher пытается подключиться заново и после восстановления отправляет актуальное состояние.

Передача состояния выполняется независимо от процессов покупателей и кассиров, поэтому сетевой код не изменяет алгоритм обслуживания.

### 3.4. Клиент-наблюдатель

Клиент реализован в `src/network_client.c`. Он устанавливает TCP-соединение, отправляет роль `OBSERVER`, принимает построчные сообщения и отображает таблицу:

- модельное время;
- число прибывших, обслуженных и ушедших без обслуживания;
- содержимое очереди каждого кассира;
- состояние каждого кассира: ожидание или обслуживание конкретного покупателя;
- признак окончания симуляции.

Клиент не имеет доступа к POSIX shared memory и не открывает семафоры. Вся информация поступает через TCP.

## 4. Динамическое подключение и отключение клиентов

Каждый наблюдатель является отдельным процессом и устанавливает собственное TCP-соединение. При нажатии `Ctrl+C` клиент закрывает свой сокет и завершается. Сервер обнаруживает закрытие соединения, удаляет соответствующую запись и продолжает обслуживать остальные подключения.

Для повторного подключения достаточно заново запустить `supermarket_client`. Сервер не требует перезапуска: новый клиент получает сохранённый последний снимок и затем продолжает получать обновления.

При завершении publisher сервер сохраняет последний снимок с признаком `finished`. Подключившийся после окончания симуляции клиент получает этот снимок и отображает завершённое состояние.

## 5. Пользовательский интерфейс и запуск

### 5.1. Сборка

```bash
make clean
make all
```

Собираются четыре исполняемых файла:

- `supermarket` - версия ИДЗ-3 с неименованными семафорами;
- `supermarket_named` - версия ИДЗ-3 с именованными семафорами;
- `supermarket_server` - TCP-сервер;
- `supermarket_client` - TCP-клиент-наблюдатель.

### 5.2. Локальный запуск

```bash
make run-network
```

По умолчанию сервер слушает порт `5555`, publisher подключается к `127.0.0.1`, а локальный клиент отображает состояние системы. Параметры можно изменить через переменные окружения `PORT`, `BIND_IP` и `SERVER_IP`:

```bash
PORT=6000 SERVER_IP=127.0.0.1 BIND_IP=0.0.0.0 ./run_network.sh config.txt
```

### 5.3. Распределённый запуск

На компьютере с сервером:

```bash
./supermarket_server 0.0.0.0 5555
```

На компьютере, где выполняется сама симуляция:

```bash
./supermarket_named init config.txt
./supermarket_named publisher <IP_СЕРВЕРА> 5555 &
./supermarket_named cashier 0 &
./supermarket_named cashier 1 &
./supermarket_named generator &
```

После завершения процессов симуляции выполняется очистка:

```bash
./supermarket_named cleanup
```

На каждом компьютере-наблюдателе запускается независимый клиент:

```bash
./supermarket_client <IP_СЕРВЕРА> 5555
```

Для гибкой настройки адрес и порт задаются аргументами командной строки, а не зашиваются в исходный код.

Пример информации, отображаемой клиентом:

```text

|              SUPERMARKET - REMOTE MONITOR (TCP)                  |
+------------------------------------------------------------------+
| Model time:     17 / 300         Snapshot: 13                    |
+------------------------------------------------------------------+
| Arrived: 10     Served: 10     Left without service: 0           |
+------------------------------------------------------------------+
| Cashier 0 queue ( 0): -                                          |
| Cashier 0 status: waiting for a customer                         |
| Cashier 1 queue ( 0): -                                          |
| Cashier 1 status: waiting for a customer                         |
```

### 6.4. Инварианты модели

Сохраняются инварианты исходного варианта:

1. Один кассир обслуживает не более одного покупателя.
2. Покупатель находится не более чем в одной очереди.
3. Вместимость очереди не превышается.
4. После завершения обслуживания покупатель покидает систему.
5. Итоговый закон сохранения: `total_arrived = total_served + total_left_no_service`.

Дополнительно проверяется, что отключение observer не влияет на ход симуляции.

## 7. Критическая оценка реализации и ограничения

1. **Изоляция симуляции от сети.** Сервер и observer-клиенты не вмешиваются в очереди и обслуживание покупателей. Это уменьшает вероятность того, что сетевые задержки изменят моделируемое поведение.
2. **Неблокирующее обслуживание клиентов.** Сервер использует `poll()` и неблокирующие сокеты. Выходная очередь каждого наблюдателя независима.
3. **Поведение медленных клиентов.** При переполнении исходящей очереди сервер отключает только соответствующего наблюдателя. Это предотвращает повреждение построчного TCP-протокола при отбрасывании части уже отправляемого сообщения. Наблюдатель может подключиться снова и получить последний снимок.
4. **Повторное подключение.** Последний снимок хранится на сервере, поэтому новому клиенту не нужно ждать следующего изменения состояния.
5. **Ограничение числа подключений.** Сервер рассчитан на 64 одновременных соединения: один publisher и до 63 observer-клиентов. Для большего количества потребовалось бы увеличить лимит и оценить сетевую нагрузку.
6. **Один источник состояния.** Один сервер обслуживает одну модель супермаркета и принимает один publisher. Поддержка нескольких независимых симуляций потребовала бы идентификатора модели в протоколе.
7. **Защита сети.** Учебный протокол не содержит шифрования и аутентификации. Его следует запускать в доверенной сети или ограничивать доступ к порту средствами сетевой защиты.
8. **Снимки, а не полная история.** Клиенты отображают актуальное состояние. При перегрузке сети медленный наблюдатель может быть отключён и затем подключиться повторно; журнал событий исходной модели остаётся в `simulation.log`.

Также добавлена проверка, что `queue_capacity` не превышает размер статически выделенного массива очереди (`MAX_QUEUE_CAPACITY`). Это предотвращает конфигурацию, для которой физического места в структуре данных недостаточно. При проверке сетевого обмена исправлено использование семафора счётчика прибывших: запись теперь синхронизирована тем же `MUTEX_STATS`, что и чтение в кассах и publisher.

## 8. Вывод

К исходной имитационной модели супермаркета добавлены TCP-сервер и независимые клиенты-наблюдатели. Сервер принимает обновления от publisher, поддерживает несколько одновременных соединений, отправляет новым клиентам последнее состояние и корректно переживает отключение отдельных наблюдателей. Сборка проходит с флагами `-Wall -Wextra -Werror`. По результатам проверки `make test` пройдены все 19 регрессионных тестов ИДЗ-3; интеграционный тест `make test-network` подтвердил работу publisher, двух одновременных наблюдателей, отключение и повторное подключение клиентов. Ручной запуск также подтвердил получение финального снимка, выполнение закона сохранения покупателей и корректную остановку сервера.
